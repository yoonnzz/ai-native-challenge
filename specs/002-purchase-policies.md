# SPEC 002: 구매·취소 정책 일괄 결정

## 승인과 상태

- 2026-09-29: AI가 제안한 23개 기준에 사용자가 “젠체 승인”이라고 답했다. 문맥상 전체 승인으로 확인하고 제안 내용과 이유를 기록한다.
- 이 문서는 승인안 1~14번을 다룬다. 아래 번호는 PROBLEM.md의 요구사항 번호와 구별한다.
- 사용자 승인 완료. 앱 구현 미착수, AI 동작 검사·사람의 화면 확인 미실행.
- 기존 [SPEC 001](001-stock-allocation.md)의 장바구니 재고 미차감·모의 주문 확정 시 재고 배정을 유지한다.

## 승인된 정책과 이유

| 승인안 | 동작 기준 | 승인된 제안 이유 |
|---|---|---|
| 1 | 무료 배송은 쿠폰 할인 전 상품 금액 기준. 30,000원 이상 무료, 미만 3,000원. 요구사항 15 유지, 27 수정. | 초기 데이터와 기본 배송 정책에 맞춘다. |
| 2 | 전체 취소 주문도 보존한다. 요구사항 22 유지, 28 수정. | 고객이 주문·취소 내역을 확인할 수 있어야 한다. |
| 3 | 다시 담기는 장바구니에만 추가한다. 요구사항 24 유지, 29 수정. | 배송지·쿠폰·금액을 다시 확인한 뒤 주문하도록 한다. |
| 4 | 품절 또는 현재 재고를 넘는 장바구니 담기·수량 증가는 거절한다. 이미 담긴 뒤 재고가 줄면 줄을 남기고 부족을 표시한다. | 주문 가능성을 안내하면서 고객이 담은 목록은 보존한다. |
| 5 | 주문 확정 때 재고·쿠폰을 재검사한다. 하나라도 문제가 있으면 주문 전체를 거절하고 이유를 표시한다. 실패 시 재고·쿠폰·장바구니는 그대로 유지한다. | 일부만 처리되는 오류를 방지한다. |
| 6 | 연속 클릭으로 중복 주문이 생기지 않게 처리한다. 여러 고객이 같은 재고를 주문해도 재고 초과 판매를 금지한다. | 먼저 성공한 주문에 재고를 배정한다는 결정을 보장한다. |
| 7 | 취소 금액은 해당 상품에 배분된 할인액을 뺀 실구매액 기준이다. 할인은 상품 금액 비례로 원 단위 배분하고 나머지는 SKU 순서로 배분한다. 동일 옵션의 반복 일부 취소는 누적 기준으로 계산한다. | 취소 순서나 반올림 때문에 환불 합계가 달라지는 오류를 방지한다. |
| 8 | 일부 취소로 배송비를 새로 부과하지 않는다. 최초 배송비는 전부 취소했을 때 반환한다. 마지막 남은 상품을 취소해도 동일하게 처리한다. | 취소 과정에서 추가 청구 없이 최종 전액 반환을 보장한다. |
| 9 | 쿠폰은 전체 취소 시 복원하고 일부 취소 시 사용 상태를 유지한다. 일부 취소로 30,000원 미만이 되어도 기존 할인을 유지한다. | 전체 취소 후 재구매를 허용하고 취소 계산을 예측 가능하게 한다. |
| 10 | 주문 당시 상품·가격·배송 정보를 주문에 별도 보존한다. 배송지 수정·삭제는 과거 주문에 영향을 주지 않는다. | 과거 거래 내역을 유지한다. |
| 11 | 다시 담기는 최초 주문 수량 기준이다. 품절·재고 부족·합산 99개 초과가 하나라도 있으면 전체 담기를 거절하고 대상을 표시한다. | 조용히 수량을 줄이거나 일부만 담지 않도록 한다. |
| 12 | 배송지 별칭·받는 사람·연락처·주소는 필수, 상세 주소·메모는 선택이다. 연락처는 하이픈·공백을 제외한 숫자 10~11자리다. 시험용 가상 정보를 사용한다. | 입력 기준을 명확하게 하고 누락을 방지한다. |
| 13 | 고객 전환 시 주문 준비 중인 배송지 선택·메모·쿠폰 적용은 초기화한다. 저장한 장바구니·찜·배송지·주문은 고객별 유지한다. 새로 담은 장바구니 줄은 기본 선택한다. | 고객 간 정보 혼동을 방지한다. |
| 14 | 쿠폰은 앞뒤 공백 제거·대소문자 구분 없이 확인한다. 선택 상품 금액이 기준 미만이 되면 적용을 해제하고 안내한다. | 입력 편의와 계산 일관성을 확보한다. |

## 원래 요구사항과의 관계

- 재고 정책은 요구사항 7·18·26, 배송비는 15·27, 취소 기록은 22·28, 다시 담기는 24·29와 연결된다.
- 나머지 정책은 장바구니·배송지·쿠폰·주문·취소 기능의 미정 처리 기준을 구체화한다. 기존 기능의 삭제나 추가 요구사항 개수로 계산하지 않는다.
- 실제 결제·환불 연동은 하지 않는다. 결제와 환불 금액은 모의 주문·취소 기록에서 처리한다.

## 구현·확인 기록

현재 수행한 작업은 승인 내용의 문서화뿐이다. 기능별 입력·실행 전 기대값·실제 결과·근거는 구현 및 실제 실행 시 추가한다. 승인 자체를 검증 완료로 간주하지 않는다.

## 후속 구현·확인 기록 (2026-09-29, 사후 정리)

위 문단은 승인 당시 상태를 보존한 것이다. 이후 `server/core.ts`에 할인 전 상품 금액 기준 배송비·단일 쿠폰, 주문 시 재고·쿠폰 재검사, 주문 당시 상품·배송지 복사, 취소 금액과 쿠폰 복원, 주문 보존, 다시 담기 정책을 구현했다. `src/main.tsx`에는 고객 전환 시 주문 준비 정보 초기화와 주문 확인 화면을 구현했다. 주문 확인 내용이 변경된 뒤 예전 확인으로 확정되지 않도록 보완한 변경은 [SPEC 009](009-order-confirmation-retrospective.md)에 따로 기록한다. `tests/shop.test.ts`의 정책 사례와 [주문 흐름 검토](007-order-review.md)의 브라우저·API 확인 기록이 근거다. 실제 결제·환불 연동은 하지 않았다. 이번 문서 보완에서 검사를 새로 실행하지 않았고, 사용자가 직접 확인한 결과도 아직 받지 않았다.
